Abstract
Cryptographic APIs are essential to application security, yet
frequent developer misuse leads to widespread vulnerabilities.
Detecting cryptographic misuse in JavaScript is challenging
due to its dynamic semantics and fragmented cryptographic
library ecosystem, which hinder static analysis tools from
accurately modeling data flows and covering non-standard or
evolving libraries, leading to high false-negative rates.
In this paper, we proposeJScamd, a static analysis frame-
work for scalable detection of cryptographic misuse in
JavaScript. JScamd integrates an enhanced program represen-
tation engine, an LLM-assisted taint rule generation pipeline,
and a precise static taint analysis engine to address JavaScript
dynamic features. Building upon 16 systematically defined
cryptographic security constraints,JScamdautomatically an-
alyzes cryptographic APIs, identifies security-sensitive taint
sources and sinks, and synthesizes comprehensive taint anal-
ysis rules. This design enables accurate detection of crypto-
graphic misuse across diverse JavaScript libraries and appli-
cation scenarios. We performed a comprehensive large-scale
evaluation on 322 widely adopted JavaScript projects.JScamd
detects 1,059 misuses and achieves 97.78% precision, signifi-
cantly outperforming three state-of-the-art tools. Our analysis
further uncovers previously unknown vulnerabilities, resulting
in 41 assigned CVEs. These results demonstrate thatJScamd
effectively bridges cryptographic security specifications and
ecosystem-scale vulnerability detection in JavaScript.
1 Introduction
Cryptography is the foundation of modern information se-
curity. In practice, its capabilities are delivered to develop-
ers through cryptographic libraries (e.g., Java Cryptography
Architecture and OpenSSL) and their application program-
ming interfaces (APIs), which encapsulate complex crypto-
graphic primitives into reusable components. Well-designed
APIs allow developers to perform cryptographic operations,

such as encryption, decryption, and key management, without
dealing with low-level implementation details. However, se-
curely using cryptographic APIs remains challenging. Devel-
opers frequently struggle to configure security parameters cor-
rectly and comply with best practices, making cryptographic
APIs highly susceptible to misuse [19, 26, 39]. JavaScript
is a prominent example of this phenomenon. As one of the
most influential programming ecosystems, JavaScript pow-
ers browser applications, Node.js-based server infrastructures,
and numerous security-critical systems [2, 15, 16, 46]. Conse-
quently, JavaScript projects increasingly rely on cryptographic
libraries to protect data transmission, authentication, and user
privacy across the web.
However, misuse of cryptographic APIs remains
widespread, mainly due to the intrinsic complexity of
cryptographic interfaces and developers relying on unreliable
external guidance, such as misleading online discussions (e.g.,
Stack Overflow) and insecure code examples generated by AI
tools [53]. Existing research has attempted to mitigate crypto-
graphic API misuse through different technical approaches.
Numerous static detectors such as CryptoGuard [39] and
Gopher [53] have been proposed. However, research focusing
on JavaScript remains scarce. First, JavaScript cryptographic
ecosystem is highly fragmented, involving browser-native
APIs [20], Node.js modules [34], and numerous third-party
libraries [31, 43], which complicates automatic identification
of cryptographic operations and construction of detection
rules. Second, JavaScript dynamic features such as dynamic
access, option object pattern and dynamic import, introduce
fundamental challenges for misuse detection [18, 25, 37].
Third, existing tools such as Semgrep [22] and Njsscan [1]
are widely used in practice, but they perform generic inter-
procedural data-flow analysis without explicitly modeling
JavaScript-specific behaviors. Meanwhile, CodeQL [17]
provides limited built-in support for cryptographic detection
rules. As a result, these tools exhibit insufficient coverage
when applied to real-world JavaScript projects.
To address these challenges, we presentJScamd, an auto-
matedJavaScriptcryptographicAPImisusedetection frame-

2 Background and Motivation
In this section, we provide the background of typical
JavaScript features and present motivating examples to il-
lustrate how these features pose unique challenges for crypto-
graphic API misuse detection.
2.1 JavaScript Language Challenges
As a dynamic, prototype-based language, JavaScript offers de-
velopers high flexibility through runtime object manipulation,
asynchronous programming, and weak typing [18, 25, 37].
However, these features significantly increase the complex-
ity of static program analysis, especially in the context of
detecting cryptographic API misuse.
Function Aliasing and Dynamic Access.JavaScript per-
mits resolving function call targets via computed property
access and variable assignment rather than static identifiers.
In practice, cryptographic API invocations are often obscured
byfunction aliasing, where methods are assigned to intermedi-
ate variables before invocation. For example, developers may
assign the encryption function to a temporary variable (e.g.,
const cipher = crypto.createCipheriv ) and invoke it

caller passes an object literal where the key-value pairs serve
as the actual arguments. While this approach improves code
readability by grouping related configurations, it obscures
the data flow for static analysis, as the function signature no
longer explicitly reveals the required parameters (e.g., crypto-
graphic keys or algorithm identifiers).

2.2 Motivating Example
The typical features of JavaScript and the variations in API de-
signs across different cryptographic libraries present a range
of technical challenges for detecting cryptographic API mis-
use. We provide a real-world code example to illustrate the
motivation behind our work.
As shown in Figure 1, Line 7 invokes CryptoJS.PBKDF2
with an insecure iteration count in Line 10. Despite the ex-
plicit vulnerability, state-of-the-art tools fail to detect it due
to two fundamental limitations:
Limited Rule Coverage.Detectors such as Semgrep and
CodeQL rely on manually curated rules to identify security-
relevant sinks. While they can effectively detect generic mis-
uses in well-known standard libraries (e.g., DES algorithm
usage in the Node.js crypto module), they provide limited
coverage for the large and diverse ecosystem of third-party
libraries such as Stanford Javascript Crypto Library (SJCL).
This limitation stems from the absence of unified or stable
API specifications across third-party packages, as well as
frequent variations in naming conventions, abstraction lay-
ers, and usage patterns. Moreover, such scanners often miss
algorithm-specific configuration issues, for example, an insuf-
ficient iteration count in PBKDF2 (Line 7). As a consequence,
achieving broad and precise coverage would require continu-
ously creating and updating library-specific rules across thou-
sands of evolving npm packages, a process that is inherently
labor-intensive.
Inability to Handle Dynamic Feature.The flexibility in-
herent in JavaScript poses significant challenges for static
vulnerability detection. As illustrated in Figure 1, Line 7 in-
vokes the PBKDF2 function from the CryptoJS library for key
derivation. Notably, this invocation adopts the options object
pattern for its third argument, where security-relevant parame-
ters, including the hashing algorithm, derived key length, and
iteration count, are encapsulated as key–value pairs within
a configuration object. Existing static analysis tools, such as
CodeQL, often fail to accurately model the data-flow relation-
ships between nested object properties (e.g., the iterations
field) and the callee PBKDF2 function. As a result, constraints
on the iteration count cannot be reliably enforced, leading to
false negatives in misuse detection.

3.1 JavaScript Cryptographic Libraries
JavaScript cryptographic libraries provide standardized inter-
faces for fundamental security operations, enabling develop-
ers to efficiently incorporate cryptographic functionality into
software systems. To understand the cryptographic ecosys-
tem in the JavaScript environment, we categorize commonly
used cryptographic libraries in different scenarios. These li-
braries are classified based on their maintainers and intended
application scope.
Official Standard Libraries.The JavaScript ecosystem
provides two primary standard cryptographic libraries: the
Web Crypto graphy API and the Node.js Crypto mod-
ule. The Web Cryptogra phy API defines a unified, strictly
asynchronous interface standardized by the W3C for web
browsers. The Node.js Crypto module, bundled with the
Node.js runtime, provides JavaScript bindings to OpenSSL,
exposing a comprehensive suite of cryptographic primitives.
It is predominantly utilized in server-side environments and
is characterized by its support for a vast array of algorithms
and flexible parameter configuration.
Third-Party Libraries.In addition to official standards,
the npm ecosystem hosts a large number of third-party crypto-
graphic toolkits. Among these libraries, CryptoJS and SJCL
(Stanford JavaScript Crypto Library) are widely used and
serve as representative examples. These libraries are imple-
mented entirely in native JavaScript and are compatible with
both browser and Node.js environments. While they are of-
ten favored for their portability and ease of integration, they
typically offer weaker security guarantees, such as permissive
defaults or insufficient parameter validation, which increases
the risk of cryptographic API misuse.
Several libraries are designed for lightweight or domain-
specific use cases. For example, Brorand focuses on ran-
dom number generation utilities, Node-RSA provides RSA-
based encryption and decryption for Node.js applications, and
libauth and ethereum-cryptography target blockchain
systems such as Bitcoin and Ethereum. Although these li-
braries are effective within their intended domains, they of-
ten provide limited algorithm coverage and weaker security
assurances, particularly when reused beyond their original
application contexts.
3.2 Cryptographic Constraints
Building upon a systematic analysis of the usability and se-
curity of JavaScript cryptographic interfaces, we establish 16
misuse detection constraints that span six dimensions: crypto-
graphic algorithm security, cipher mode security, key lifecycle
security, random number security, cryptographic protocol se-
curity and secure storage of sensitive parameters, as shown
in Table 1. Among these constraints, C-01 covers insecure
cryptographic algorithms and requires a finer-grained decom-
position because different algorithm families expose differ-
ent security parameters and misuse patterns. Therefore, we
further divide C-01 into five sub-constraints, covering inse-
cure symmetric-key algorithms, asymmetric-key algorithms,
elliptic-curve parameters, hash functions, and HMAC con-
structions, as summarized in Table 2. This decomposition
allows JScamd to map high-level algorithm-security require-
ments to concrete JavaScript API patterns and parameter
checks across different cryptographic libraries. These con-
straints are formulated with reference to up-to-date interna-
tional standards and widely recognized security best prac-
tices [7, 12, 13, 20, 23, 24, 28, 44]. Furthermore, to account
for the unique characteristics of JavaScript-based web devel-
opment, we introduce additional constraints (e.g.,C-15and
C-16) targeting cookie-related APIs, enhancing the security
of sensitive parameter storage in web scenarios. Based on our
systematic analysis of JavaScript cryptographic library APIs,
each constraint is explicitly mapped to the corresponding API
design and usage patterns, ensuring their practicality and ap-
plicability in real-world systems. The detailed explanations
of the security rationale behind each constraint are provided
in Appendix A.1.

Enhanced Program Representation Engine.To enable
precise static taint analysis for the detection of cryptographic
API misuse in JavaScript,JScamdincorporates an enhanced
program representation engine that transforms JavaScript
source code into a lightweight cryptography-aware intermedi-
ate representation (IR). Starting from an abstract syntax tree
(AST), the engine extracts semantic facts that are consumed
by the taint analysis engine. Specifically, the engine tracks as-
signments and variable flows, normalizes JavaScript member
expressions into canonical API paths, summarizes function
parameters and return flows, and materializes call sites and
object fields with lexical scope information. These IR facts
explicitly capture security-relevant JavaScript semantics. By
preserving scope-sensitive and field-sensitive data-flow in-
formation, the enhanced representation provides a precise
foundation for downstream taint analysis.
LLM-assisted Taint Analysis Rule Generation Pipeline.
To overcome the scalability and coverage limitations of manu-
ally written taint-analysis rules,JScamdincorporates an LLM-
assisted rule generation pipeline that automatically transforms
natural-language cryptographic API misuse descriptions into
executable static taint rules. The pipeline combines crypto-
graphic library documentation, structured misuse specifica-
tions, and static-analysis constraints to guide the model in
producing rules that conform toJScamdinternal schema. By
extracting API candidates, semantically mapping APIs to mis-
use definitions, and instantiating formal source–sink rules,
JScamdenables rapid adaptation to new cryptographic li-
braries and evolving misuse patterns. To ensure correctness
and executability, the generated rules are validated through
automated consistency checks and an iterative self-correction
loop, yielding a continuously extensible and up-to-date rule
base for static cryptographic API misuse detection in the
JavaScript ecosystem.
Precise Static Taint Analysis Engine.To accurately de-
tect cryptographic API misuses in JavaScript,JScamdinte-
grates a precise static taint analysis engine that tightly couples
rule-driven reasoning with fine-grained propagation tracking.
Guided by formally defined taint rules, the engine dynami-
cally constructs inter- and intra-procedural propagation paths
over the enhanced program representation, recording insecure
data flows through blacklist and context-aware propagation
structures. To accommodate diverse cryptographic usage pat-
terns,JScamdsupports multiple complementary taint analy-
sis frameworks, including single-point identification, forward
tracking, backward tracking, and hybrid analysis, each tai-
lored to different API designs and misuse scenarios. By flexi-
bly combining these analysis strategies,JScamdcan reason
about complex, multi-stage cryptographic behaviors and re-
liably identify security violations that are typically missed
by conventional static analyzers in the presence of JavaScript
dynamic features.

(1) Design of Cryptography-Aware Intermediate Repre-
sentation.JScamdaccepts JavaScript code from individual

For a projectP, the IR is organized as:
IR(P) =⟨V c,Vm,F,C,O,S⟩,
Each component captures one category of program informa-
tion required by the taint rules. The constant-binding compo-
nent Vc records variables whose values can be statically re-
solved to literals, together with their source locations and valid
lexical scopes. The variable-binding component Vm records
assignments, aliases, and symbolic expressions whose values
may depend on other variables, member paths, function re-
turns, or composed expressions. The function-summary com-
ponent F records each function’s name, formal parameters,
return expressions, source location, and scope. The call-site
component C records normalized callees, ordered arguments,
object-literal arguments, source locations, and scopes. The
object-field component O records property-level bindings ex-
tracted from object literals and member assignments. Finally,
the scope component S records lexical intervals used to decide
whether a definition is visible at a use site.
(2) Intermediate Representation Generation from Raw
AST.JScamd processes the raw AST to generate IR for as-
signments, declarations, member expressions, object expres-
sions, function definitions, and call expressions.
Step 1: Tracking Assignments and Variable Flows.The
first step extracts value flows from variable declarations and
assignment expressions. Literal assignments are recorded
in the constant-value component Vc, whereas assignments
whose right-hand side is an identifier, member path, call ex-
pression, binary expression, or template literal are recorded
as symbolic dependencies in the mutable-binding component
Vm. Instead of immediately resolving these dependencies, JS-
camd preserves them as analysis facts so that aliases, object
paths, and derived values can be resolved during later taint
propagation. This design is necessary because cryptographic
APIs in JavaScript are often invoked indirectly. As shown
in Figure 3, const enc = crypto.createCipheriv at

ings, template literals, or bounded expressions. If the property
cannot be resolved statically, JScamd retains it as a symbolic
property dependency for later propagation. This preserves dy-
namic access information without forcing unsound resolution.
Step 3: Function summaries for inter-procedural flows.
The third step builds lightweight function summaries for inter-
procedural propagation. For each function declaration or func-
tion expression, JScamd records its name, formal parameters,
return expressions, source location, and lexical scope in F.
Return expressions may be literals, identifiers, member paths,
object fields, or call results. When a function call result is
assigned to a variable or object field, JScamd links the re-
ceiving binding to the callee’s return summary whenever the
callee can be statically resolved. This design is important be-
cause security-sensitive values are often computed in helper
functions before reaching cryptographic sinks. For instance,
an IV may be initialized as a constant as shown at Line 2
in Figure 3, returned by getIV() at Line 5, stored in the ob-
ject field opts.iv at Line 10, copied into the local variable
iv at Line 13, and eventually passed to the third argument
of createCipheriv at Line 14. Function summaries make
these cross-function dependencies explicit in the IR, allowing
the taint engine to recover flows that are not visible from the
sink call alone.
Step 4: Materializing call sites and object fields.For each
call expression or constructor expression, JScamd creates a
call-site record in C, including the normalized callee, ordered
arguments, source location, and lexical scope. The ordered
argument list is important because many cryptographic rules
are position-sensitive. JScamd further represents configura-
tion objects using field-sensitive facts. Many JavaScript cryp-
tographic APIs, such as the Web Cryptography API, pass
security-relevant parameters through configuration objects
rather than positional arguments. Accordingly, JScamd ex-
tracts object literals and property assignments into explicit
field records in O. For example, JScamd represents the object
literal {name: "AES-CBC", iv: x} at Line 10 of Figure 3
as two field-level IR records, one for name and the other for
iv. This field-sensitive representation allows JScamd to dis-
tinguish algorithm names, IVs, salts, iteration counts, keys,
and certificate-validation flags even when they appear in the
same configuration object. Finally, JScamd associates each
call-site and field-level record with its lexical scope. During
dependency resolution, JScamd only considers definitions that
are visible at the corresponding use site. This scope-aware
design prevents arguments or object fields from being linked
to unrelated definitions, thereby reducing spurious data-flow
propagation.
4.3 LLM-assisted Taint Analysis Rule Genera-
tion Pipeline
Traditional static taint analysis frameworks rely heavily
on manually written taint rules, each describing specific
⟨source,sink,f ilter⟩ relationships. Such manual efforts are
not only time-consuming but also incomplete, as new crypto-
graphic APIs and misuse scenarios continuously emerge. To
overcome this limitation,JScamdintroduces an LLM-assisted
rule extraction and source/sink labeling framework that au-
tomatically transforms natural-language misuse descriptions
into deployable static taint rules consistent withJScamdin-
ternal rule schema.
The framework aims to automatically generate structured
taint analysis rules for cryptographic API misuse detection
by combining library-specific knowledge, natural-language
misuse definitions, and static analysis constraints. Given the
source code or documentation of a JavaScript cryptographic
library, the LLM extracts all available API definitions, infers
their functional categories, identifies security-relevant param-
eters, and finally outputs rule objects directly executable by
theJScamdengine. In this way,JScamdcan be extended
to new cryptographic libraries without manual engineering
effort, ensuring scalability and adaptability.
Our experiments reveal two primary difficulties in LLM-
assisted rule extraction. First, large models often lack deep
understanding of specific cryptographic APIs, occasionally
hallucinating unsupported modes (e.g., “AES-OFB”) or misla-
beling parameter semantics. Second, the models are unaware
of the static analyzer’s internal logic, sometimes generating
unrecognized fields (e.g., nonexistent judge functions). We
address these through prompt-level alignment—explicitly en-
coding analyzer constraints, white-listed APIs, and validated
examples—allowing the model to generate executable and
verifiable taint rules that integrate seamlessly withJScamd.
The overall workflow of the LLM-assisted rule generation
framework consists of three main stages:
(1) API Extraction And Preprocessing.Using the AST
construction module,JScamdparses each cryptographic li-
brary’s source code to extract candidate APIs. JavaScript
libraries typically include both user-facing functions (e.g.,
subtle.encrypt, AES.encrypt) and numerous internal

--- PAGE 9 ---
helpers (e.g., _deriveBytes, toString). To ensure analy-
sis precision, we filter out irrelevant APIs through keyword-
based heuristics (e.g., encrypt, hash, sign, derive, iv) and
semantic matching of parameter lists. The resulting API can-
didate list forms the foundation for subsequent reasoning.
(2) LLM-assisted API Semantic Mapping.Each API can-
didate is paired with a corresponding natural-language misuse
rule and minimal contextual knowledge (e.g., the API’s func-
tion description and parameter names). The LLM receives this
structured input and determines whether the API semantically
matches the misuse description. The detailed prompt design
and decision workflow are illustrated in Figure 6 in the Ap-
pendix A.2. This classification process transforms descriptive
security constraints into API and parameter associations that
form the basis for taint rule instantiation.
(3) Rule Construction And Labeling.After identifying
relevant API–rule pairs, the model instantiates formal taint
rules usingJScamd’s internal rule() constructor. To ensure
that the LLM-generated taint-analysis rules are semantically
accurate and executable inJScamd, we design a structured
prompt template that guides the model’s reasoning and con-
strains its generation space. As shown in Figure 7 in the
Appendix A.2, the prompt consists of four main sections: the
task instruction, knowledge context, framework constraint,
and one-shot demonstration. Each section provides distinct
yet complementary information that guides the LLM to gen-
erate accurate and executable taint analysis rules for crypto-
graphic API misuse detection.
The task instruction specifies the overall objective and out-
put format, instructing the model to produce a JavaScript
rule object compatible withJScamdstatic analysis engine.
The knowledge context incorporates the natural-language de-
scription of the misuse rule and relevant information from
the cryptographic library’s API, including function names, pa-
rameter descriptions, and algorithm categories. For instance,
when generating a rule for the misuse“Do not use constant IV
in AES-CBC mode”, this section provides the model with the
API signature subtle.encrypt(algorithm, key, data)
and identifiesivas the security-sensitive parameter.
The framework constraint section encodes the operational
semantics ofJScamdanalyzer, including supported fields,
taint sources, sinks, and judgment functions. This ensures
that the model’s output adheres to the syntactic and semantic
conventions of the taint engine, thus avoiding incompatible
or non-executable rules. The one-shot demonstration section
then provides one or two verified examples of correct rule
definitions, allowing the model to infer the expected structure
and stylistic conventions.
When constructing the prompt, we also dynamically adjust
the content length to maintain efficiency. If the library docu-
mentation or API list is excessively long, we retain only the
subset of APIs directly related to the targeted misuse cate-
gory (e.g., encryption, hashing, and key derivation) to avoid
exceeding model context limits.
We expect the LLM to respond in structured JSON format,
where each field of the rule object is instantiated according
to the analyzer’s schema, as shown in Figure 4. The model
is instructed to produce both the rule definition and an ac-
companying brief explanation describing its reasoning, as this
“generate-then-justify” pattern consistently produces more sta-
ble and interpretable outputs. Furthermore, when the model
determines that a misuse rule does not apply to the given
API, it explicitly indicates the reason (e.g., “unsupported al-
gorithm” or “no related parameter”), which allowsJScamdto
prune irrelevant mappings and reduce redundant LLM calls.
This design allows the model to generate rules that are both
syntactically compliant and semantically aligned with real
cryptographic API behaviors, thereby bridging the gap be-
tween high-level natural-language misuse descriptions and
executable static analysis constraints.

4.4 Precise Static Taint Analysis Engine
To enable context-aware detection of cryptographic API mis-
use in JavaScript, JScamd employs a static taint analysis en-
gine that combines rule-guided reasoning, dynamically con-
structed propagation paths, and fine-grained taint tracking. Un-
like conventional approaches based on fixed pattern matching
or shallow flow inspection, our engine couples security rule
semantics with program-level data dependencies, enabling
precise reasoning about multi-stage cryptographic usage.
(1) Rule Mapping And Dynamic Path Construction.
Once the element lists are established (functions, calls, vari-
ables, constants, and objects),JScamdinitializes rule mapping
by loading corresponding taint rules derived from the rule
repository. Each rule defines the triplet ⟨source,sink,f ilter⟩
and specifies the expected flow conditions. For instance, the
misuse rule C-04 forbids the use of a constant IV in block
cipher modes. The constant iv is initialized by a deterministic
buffer as thesource; the call tocrypto.createCipheriv()
represents a cryptographic sink; and no randomization filter
such as crypto.randomBytes() exists in the propagation
path. Consequently, the taint engine records the variable iv
in the blacklist and reports a violation of ruleC-04.
(2) Propagation Tracking And Blacklist Recording.Dur-
ing analysis,JScamddynamically constructs both inter and
intra propagation paths by linking element nodes through AST
indices. Each intermediate propagation is logged in auxiliary
structures, including:Propagation Tablesfor recording cross-
scope variable dependencies;Blacklistsfor marking insecure
or unfiltered taint elements;Context Mapsfor correlating call
expressions with their lexical environments. The engine con-
tinuously updates these lists during traversal to ensure that any
unfiltered data flow from insecure sources to cryptographic
sinks can be precisely reported. This fine-grained propagation
modeling enablesJScamdto detect misuse patterns that are
typically invisible to conventional static analysis tools limited
by JavaScript’s dynamic nature.
(3) Four Kinds of Taint Analysis Frameworks.Based on
cryptographic interface design and common calling scenarios,
we design four complementary taint analysis frameworks.
Single-Point Identification Framework.This framework
directly identifies unsafe points by detecting parameters or
cryptographic methods that violate security standards. Once
identified, a misuse alert is generated. When the risk point
is clearly defined and can be easily located in the AST, this
approach provides fast and efficient detection. For example, in
CryptoJS and SJCL, symmetric algorithms are implemented
as classes and encryption operations are invoked through
specific algorithm classes such as AES or DES. According
to ruleC-01, DES is considered insecure for practical use;
therefore, any DES invocation can be directly classified as
misuse. Similarly, weak hash algorithms such as RIPEMD-
160 and SHA-1 can be directly flagged as security risks.
Forward Taint-Tracking Framework.The forward taint-
tracking framework analyzes the propagation path from a
source to a sink. It is widely used in static analysis and is
particularly suitable for scenarios where pollution sources
can be explicitly identified. It requires that risky variables or
method calls possess distinctive characteristics and are easy
to locate. In Node.js Crypto, encryption functions targeted by
rules for insecure algorithms (C-01), ECB-mode encryption
(C-03), non-random IVs (C-04), and others commonly invoke
createCipheriv(). The selection of algorithms, modes, and
other parameters is performed via method arguments. For mis-
use detection, we first identify variables associated with the
algorithm or working mode, and then analyze the information
flow in the AST to determine whether the tainted source prop-
agates to the sink point. This forward analysis traces tainted
information and exposes potentially unsafe configurations or
misuse instances.
Backward Taint-Tracking Framework.The backward taint-
tracking framework analyzes propagation starting from the
sink to identify the corresponding source. It is primarily used
when the source cannot be explicitly defined but can be in-
ferred from indications provided by the sink. Implementing
rules such asC-01andC-09is challenging because their
sources are often common values without clear distinguishing
features. For such detections, we begin from an aggregation
point. We first identify APIs that pose aggregation risks, such
as key derivation functions or key generation functions, and
then trace backward to recover the original value that was
passed in. The traced parameter can correspond to either the
argument position targeted by the analysis or a key value
within an option structure.
Hybrid Taint-Tracking Framework.The hybrid framework
combines forward and backward analysis and is designed to
handle scenarios involving multi-directional dependencies,
where multiple pollution sources may traverse the same sink.
The design is driven by two practical detection requirements.
First, it supports randomness assessment of IVs in CBC and
CFB modes, where the two pollution sources to be located
are the block cipher working mode and the IV . Second, it
addresses security-flag assessments for cookies that store sen-
sitive information, where the two pollution sources to be
located are the sensitive data itself (e.g., JWT or session ID)
and the security flag (e.g.,HttpOnly). The core idea is to first
use one pollution source to determine whether a risk scenario
is present; if a potential risk is established, the analysis then
searches for another pollution source to confirm whether an
actual misuse has occurred.

5.4 Effectiveness of Enhanced Program Repre-
sentation Engine
To better quantify the effectiveness of the enhanced program
representation engine inJScamd, we compare it with Semgrep,
Njsscan, and CodeQL on the Obuhersys dataset [4], as shown
in Table 5. Obuhersys is a benchmark designed to evaluate
cryptographic misuse detection under complex JavaScript pro-
gram features. Unlike simple static samples that contain direct
API calls and constant parameters, Obuhersys incorporates
inter-procedural data propagation, context-sensitive calls,
path-sensitive conditional branches, field-/object-sensitive
data transfer, and combinations of multiple sensitivity require-
ments. These features make cryptographic misuses appear
only after variables, function calls, object properties, wrapper
functions, or conditional branches are resolved, thereby pro-
viding a more challenging setting for evaluating the semantic
modeling capability of static analysis tools. The Obuhersys
dataset is constructed based on the Node.js Crypto library.
To ensure a fair comparison, we evaluate only the security
constraints that are supported by all tools, including insecure
cryptographic algorithms (C-01-a), insecure hash algorithms
(C-01-d), ECB-mode encryption (C-03), insecure IV usage in
block cipher modes (C-04/C-05), and weak PBKDF2 config-
urations (C-09/C-10). The results show thatJScamdachieves
the best overall balance between detecting true misuses and
controlling false positives on this challenging dataset. Com-
pared with Semgrep,JScamdsubstantially improves recall
from 6.67% to 38.33% and F1 score from 11.76% to 46.46%,
indicating that pattern-based matching alone is insufficient
for capturing cryptographic misuses hidden behind JavaScript
data propagation. Compared with Njsscan,JScamddetects
slightly more true positives while producing fewer false posi-
tives, leading to higher precision, recall, and F1 score. Com-
pared with CodeQL,JScamdachieves much higher recall

We further analyze the sources of false negatives and false
positives produced byJScamdon this dataset. The false nega-

class constructors, and static factory methods. To avoid intro-

and field-assignment scenarios,JScamdadopts a relatively
conservative propagation strategy. As a result, when an in-
secure value is indirectly propagated to a cryptographic API
through object fields, constructor-returned objects, or factory
methods, the complete flow may not always be recovered.
Second,JScamddoes not yet perform precise path-sensitive
analysis for branch conditions. Therefore, in samples where
the misuse depends on branch reachability,JScamdmay fail
to determine whether an insecure value necessarily reaches
a sensitive cryptographic call. These false negatives mainly
reflect the inherent trade-offs of static analysis in field sensi-
tivity, context sensitivity, and path sensitivity. They are not a
JScamd-specific failure pattern; instead, they reflect a broader
limitation shared by static analysis tools when analyzing dy-
namic JavaScript programs. We also examine the sources
of false positives. False positives mainly occur in scenarios
involving custom identity functions, factory methods, higher-
order function wrappers, and complex path conditions. When
string-based rules cannot fully resolve runtime values,JScamd
may mistakenly interpret keywords appearing in variable or
field names as actual cryptographic algorithm values. De-
spite these limitations, the overall results show thatJScamd
achieves the best recall and F1 score, suggesting that it im-
proves the coverage of cryptographic misuse detection while
maintaining a practical trade-off between false negatives and
false positives, which is a common challenge for static analy-
sis tools.

6 Limitation and Discussion
Similar to prior work [10, 26, 39],JScamdhas limitations that
warrant future improvement.
Detection Accuracy.Most observed false positives stem
from ambiguities caused by APIs sharing identical names.
SinceJScamdfocuses on identifying key APIs and parame-
ters rather than inferring concrete algorithmic semantics, it
may misinterpret similarly named functions or orthogonal
calls, as also noted in prior work such as CryptoGuard [39]
and CryptoGo [26]. In response to the false-positive con-
cerns raised by Chen et al. [10], we attempt to constrain the
security context when defining rules (e.g., treating insecure
PRNGs as misuse only when used for security-critical cryp-
tographic operations). However, existing tools still struggle
to precisely determine the security intent of API usage. In
addition, false negatives may occur when security-sensitive
values are propagated through complex JavaScript features,
such as object fields, factory methods, higher-order wrappers,
or path-dependent branches. These cases require more precise
field-, context-, or path-sensitive reasoning, which remains
challenging for static analysis tools. Future integration of
machine-learning–based semantic understanding may further
reduce false positives and false negatives.
Language and Transformation Scope.JScamd operates
on standard JavaScript and does not natively support Type-
Script. Because TypeScript introduces extended syntax (e.g.,
type annotations and generic declarations), its raw source files
cannot be directly processed by our current Esprima-based
AST module. However, this is an engineering limitation of
the frontend rather than a flaw in our taint analysis design.
Future iterations can resolve this by integrating TypeScript-
aware parsers. Second, JScamd does not currently handle
heavily minified or obfuscated JavaScript code. These trans-
formation techniques intentionally destroy formatting, flatten
control flows, and obscure data dependencies. Such struc-
tural alterations hinder JScamd from accurately constructing
taint propagation paths. Consequently, our current evaluation
focuses on source-level repositories. Handling transformed
code would require dedicated preprocessing (e.g., source-map
recovery and de-obfuscation), which is left for future work.
LLM Dependence and Model Evolution.JScamdre-
lies on large language models for semantic rule generation.
As foundation models rapidly advanced, we revisited our
pipeline with more recent LLMs and observed noticeable im-
provements in semantic coherence, stability in API–misuse
mapping, and correctness in taint rule instantiation. These
4934    35th USENIX Security Symposium USENIX Association

--- PAGE 16 ---
observations suggest that our approach is inherently model-
agnostic and can benefit from continual progress in LLM
technology. It is also worth noting that all quantitative exper-
imental results reported in this paper are based on the most
recent dataset collected in December 2025, ensuring that the
evaluation reflects contemporary cryptographic library imple-
mentations and practical misuse patterns.
LLM-agent Based Analysis.We also conducted a supple-
mentary evaluation using an LLM-agent. Specifically, we ap-
plied Codex [35] to analyze the real-world project MeshCen-
tral, which contains 132 JavaScript files and approximately
107,390 lines of JavaScript code. The agent-based analysis
cost $2.3 for this single project, yet it identified only 13 of
the 42 true positives detected by JScamd. This result suggests
that directly applying LLM agents to repository-level cryp-
tographic misuse detection remains less effective and less
cost-efficient than JScamd rule-guided static analysis.
Responsible Disclosure.Based on the findings summa-
rized in Table 3, we contacted developers of affected projects
and followed responsible disclosure practices. Among 124
contacted projects, maintainers of 23 projects provided sub-
stantive responses as of May 2026. Specifically, 12 projects
confirmed the reported issues, and some have implemented
fixes or security improvements; for example, bcoin upgraded
its hashing algorithm to SHA-256. Other maintainers argued
that weak cryptographic primitives were used in non-security
contexts (e.g., meteor, whistle), or that insecure designs
were constrained by legacy protocols, reverse-engineering
requirements, or deployment assumptions (e.g., tuyapi, io-
Broker.mihome, MeshCentral). The disclosure process re-
flects a common gap between cryptographic misuse patterns
and developers’ perception of practical exploitability. Similar
response patterns have also been observed in prior crypto-
graphic misuse studies, where confirmation and remediation
rates were limited despite technically valid reports [39]. In
total, we obtained 41 CVE IDs, 21 of which are currently
under embargo and have not yet been publicly disclosed.
7 Related Work
Cryptographic API Misuse Detection.Numerous studies
have demonstrated that cryptographic API misuse is pervasive
across real-world software ecosystems. Early research pre-
dominantly focused on Java-based applications, where tools
such as CryptoLint [14], CryptoGuard [39], JWTKey [50] and
Crylogger [36] systematically analyzed Java Cryptography
Architecture (JCA) usage to detect cryptographic API misuse
using static or dynamic analysis techniques. These works re-
vealed that developers frequently misuse cryptographic APIs
due to complex interfaces, insufficient guidance, or misunder-
standing of security guarantees. Subsequent research efforts
extended cryptographic API misuse detection beyond Java to
a broader range of languages and platforms, consistently con-
firming that the problem is not language-specific but rather a
widespread software engineering challenge. Empirical anal-
yses have identified large-scale cryptographic API misuses
in C/C++ [51], Python [19, 47], and Go [26, 53], with a sig-
nificant proportion of projects exhibiting issues. In recent
years, the industry has also introduced multi-language static
analysis tools such as CodeQL [17] and Semgrep [22], which
provide cryptography-related detection rules. However, these
general-purpose multilingual tools often struggle to handle
language-specific characteristics effectively and lack domain-
specialized cryptographic detection capabilities.
JavaScript Static Analysis and Security Detection.
JavaScript static analysis has been widely studied. However,
the features of the JavaScript language make it difficult to pre-
cisely recover control flow, call relationships, and data depen-
dencies [18]. Flow [9] demonstrates that scalable static type
checking can be deployed on large JavaScript code bases. The
event-driven analysis for Node.js [32] applications and mod-
ular call-graph construction address callback relationships,
module boundaries, and cross-package analysis in server-side
JavaScript. Security-oriented JavaScript analysis commonly
relies on taint tracking and dependence modeling. Wei et
al. [45] combine runtime information, such as object types,
dynamically generated code, and execution traces, with static
taint analysis to mitigate the imprecision and timeout prob-
lems of purely static JavaScript analysis. TAJS/TAJStaint-
based work [3] integrates abstract interpretation, string au-
tomata, and rendering-context-aware sanitization to detect
DOM-based XSS. More recently, ODGen [25] proposes an
object dependence graph that uniformly models JavaScript
objects, AST nodes, control-flow dependencies, and data de-
pendencies, and uses graph queries to detect Node.js vulner-
abilities such as command injection, path traversal, and pro-
totype pollution. Several studies are more closely related to
JavaScript API misuse detection and taint-model construction.
SAFEWAPI [5] detects Web API misuses using predefined
misuse patterns, demonstrating the feasibility of rule-based
API misuse detection in web applications. Staicu et al. [42]
automatically extract taint specifications, including sources,
sinks, and propagators, for JavaScript libraries to reduce the
manual effort of maintaining taint models.
Existing studies focus heavily on low-level program se-
mantics (e.g., types and taints) but lack a rule-facing abstrac-
tion that directly exposes security-sensitive API contexts. JS-
camd bridges this gap with a security-oriented IR that distills
volatile dynamic patterns into stable semantic records, en-
abling direct and robust misuse detection
LLM-Assisted Security Analysis.Meanwhile, Large Lan-
guage Models (LLMs) have achieved remarkable success in
various real-world security analysis tasks. Researchers have
begun exploring the integration of LLMs with programmable
analysis frameworks to address more complex and semanti-
cally rich problems [11, 27, 29, 49, 52]. IRIS [27] proposed an
LLM-assisted static analysis framework that leverages Cod-
eQL for program analysis while using LLMs to label APIs
USENIX Association 35th USENIX Security Symposium    4935

--- PAGE 17 ---
and associate them with vulnerability patterns.
Cryptographic API Usability.There are also studies that
focus on improving the usability of cryptographic libraries,
examining how interface design, API complexity, documenta-
tion quality, and abstraction mechanisms influence developers’
ability to correctly and securely apply cryptographic function-
ality [2, 8, 30, 41, 48, 54]. While these studies reveal important
design flaws and usability barriers, they largely stop short
of detecting or quantifying concrete misuse in large-scale
real-world JavaScript systems.
Compared with the above work,JScamdfills an impor-
tant gap by providing a specialized framework dedicated to
analyzing cryptographic API misuse in JavaScript applica-
tions. By leveraging enhanced static taint analysis techniques
and LLM-guided rule generation,JScamdassists developers
in identifying and mitigating cryptographic vulnerabilities,
thereby improving the security of JavaScript applications that
rely on cryptographic operations.
8 Conclusion
In this paper, we presentJScamd, an innovative framework
for detecting cryptographic API misuse across the JavaScript
ecosystem.JScamdaddresses the challenge of detecting cryp-
tographic misuses in JavaScript through static taint analysis
by combining an LLM-assisted rule generation pipeline with
a JavaScript-specific program representation and taint anal-
ysis engine. This design transforms natural-language cryp-
tographic constraints into executable analysis rules while
preserving security-relevant JavaScript semantics, enabling
accurate taint propagation and misuse detection across dy-
namic language constructs. Through comparative evaluation
against SOTA tools, we demonstrate the effectiveness ofJS-
camd. Applying our framework to 322 popular JavaScript
projects, we identify 1,059 real-world misuse instances with
a precision of 97.78%. Our findings provide the first compre-
hensive empirical understanding of cryptographic API misuse
in the JavaScript community.

A.1 Details of Security Constraints
Cryptographic Algorithm Security.Secure cryptographic
algorithms are fundamental to ensuring the confidentiality and
integrity of security systems. According to NIST SP 800-57,
cryptographic mechanisms must provide sufficient security
strength to withstand current and foreseeable computational
capabilities, and the minimum required strength is expected
to increase to 112 bits by 2030 [7].C-01prohibits the use of
weak or deprecated cryptographic algorithms. We further clas-
sify weak algorithms into several subclasses.C-01-arestricts
the use of insecure symmetric encryption algorithms, such as
DES and TDEA (Triple Data Encryption Algorithm). In par-
ticular, NIST mandates that TDEA must no longer be used for
encryption after 2023 and may only be retained for backward-
compatible decryption [6];C-01-bconcerns the secure use
of asymmetric algorithms and prohibits key strengths below
recommended thresholds, such as weak RSA or DSA param-
eters;C-01-crequires elliptic curve cryptography (ECC) to
employ curves with a field size of at least 224 bits to ensure
adequate security strength;C-01-dforbids the use of broken
hashing algorithms that can no longer provide collision resis-
tance;C-01-eprohibits insecure MAC constructions, such as
HMAC-MD5, which are known to pose security risks.C-02
prohibits the use of insecure Diffie–Hellman groups, includ-
ing modp1, modp2, and modp5. This rule is also derived from
security strength considerations. These DH groups provide
key lengths of less than 2048 bits, significantly weakening
the security guarantees of IPSec negotiations and other cryp-
tographic protocols. Therefore, they should be replaced with
stronger DH groups that meet modern security strength re-
quirements.
Cipher Mode Security.The rules governing block cipher
modes includeC-03,C-04, andC-05. RuleC-03disallows
the use of ECB mode, as identical plaintext blocks produce
identical ciphertext blocks, leaking structural information and
enabling pattern-based attacks. RuleC-04requires that initial-
ization vectors (IVs) in CBC and CFB modes be random and
unique. Complementarily, ruleC-05enforces IV uniqueness
across block cipher modes. In modes such as CTR and OFB,
the IV must be unique for each encryption. In addition, rule
C-06addresses asymmetric encryption padding, recommend-
ing modern schemes such as PSS and OAEP over the legacy
PKCS1-v1.5 algorithm.
Key Lifecycle Security.C-07andC-08concern the use
of predictable keys and salts in cryptographic functions, par-
ticularly in key derivation. Such practices can weaken the
randomness of keys and have a negative impact on the secu-
rity of the application.C-09andC-10further require sufficient
iteration counts and adequate key lengths in key derivation
functions, thereby enhancing resistance against brute-force
and related attacks by increasing the computational cost for
adversaries.
Random Number Security.C-11advises against using
unsafe random number generators, particularly unsafe pseudo-
random number generators in software. In JavaScript cryp-
tographic libraries, there are two types of PRNGs available:
(a) Statistical PRNGs, such as Math.random(), rely on de-
terministic algorithms and can be predicted through statisti-

--- PAGE 21 ---
cal analysis, making them unsuitable for security-sensitive
applications. (b) Cryptographic PRNGs provided by cryp-
tographic libraries generally offer stronger randomness and
can meet security requirements. However, caution is still re-
quired, as some third-party implementations (e.g., CryptoJS)
may fallback to weak randomness sources such as time- and
counter-based generators, which introduce security risks.
Cryptographic Protocol Security.Secure configuration
of cryptographic protocol suites is essential to protect commu-
nication channels.C-12prohibits the use of insecure HTTP
parsers to prevent the acceptance of malicious input.C-13re-
quires strict certificate validation to ensure that only legitimate
entities are authenticated and allowed to establish connections.
C-14discourages the use of weak SSL/TLS versions (e.g.,
SSLv3, TLS 1.0, TLS 1.1), which are vulnerable to attacks
such as BEAST, BREACH, and CRIME [40].
Secure Storage of Sensitive Parameters.C-15andC-16
emphasize the importance of implementing proper security
measures when storing sensitive security parameters in cook-
ies. In particular, precautions should be taken to mitigate XSS
and related client-side attacks. Therefore, user identity tokens
and session identifiers should be stored in cookies with the
HttpOnly attribute enabled, ensuring that they cannot be ac-
cessed or modified by client-side scripts. Prior studies have
demonstrated that disabling HttpOnly allows JavaScript to
read or tamper with cookie attributes, which significantly en-
larges the attack surface. Moreover, insecure cookie handling
may facilitate CSRF exploitation, where a compromised JWT
stored in a cookie can be leveraged to initiate forged requests
on behalf of the victim.
