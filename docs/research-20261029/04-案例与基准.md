## 本次整理的40个验证场景

详细条件在 [cases.md](examples/cases.md)，可直接用 [CSV](examples/cases.csv) 做人工标注表。每行包含：目标、正反条件、预期分类、依据、观测器、现有F族对应及状态。统一状态为 `proposed_not_executed`，不是新添的40个已跑通工程。

建议分层：

1. 第一轮选择 K01–K10、K18–K23、K25–K28，验证句柄/材料、包装、Native输出、清零基本语义。
2. 第二轮加入控制流、上下文、字段、多秘密及跨域恢复 K11–K17、K34–K40。
3. 第三轮加入状态持久化、nonce、低熵派生和动态观测 K24、K29–K33。

原 F1–F8 的“A_Safe/B_Risky”只是设计意图。不要自动将目录名复制为ground truth；例如受保护包装需要真 API 和访问控制成立，copy buffer负例需要排除其他可读副本，摘要负例需要高熵输入条件。

## 最小实验表达式（仅语义示意，不是可编译SDK代码）

```text
K01: secret_handle_alias -> persist                 => 不泄露密钥材料；授权滥用另判
K02: secret_bytes -> Base64 -> persist_and_flush    => 存储可读者可恢复
K07: wrap(secret, protected_KEK) -> Base64 -> store => 若KEK与解包能力均不可得，不能直接恢复
K08: store(wrap(secret, KEK)) + store(KEK)           => 两者均可读时可以恢复
K18: p -> external_arraybuffer -> full_zero(view)   => 同一有效区域清零；历史副本另判
K19: p -> buffer_copy(q) -> full_zero(q)            => p仍是独立原件
```

辅助函数需要落实到已固定版本的官方API；不要将这些表达式复制成不存在的 `huks.wrapKey` SDK调用。
